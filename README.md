## 배포 방법

1. `index.html`을 GitHub 저장소 최상위에 업로드해 기존 파일을 교체합니다.
2. **이 `README.md`도 같은 저장소 최상위에 업로드**해 기존 README가 있다면 교체합니다.
3. GitHub Pages가 `main` 브랜치의 `/ (root)`로 설정되어 있는지 확인합니다.
4. 사이트 새로고침 후 상단 버전 번호가 `v6.3`인지 확인합니다.

## 운영 시 주의

관리자 권한 및 예약 데이터 접근이 Firebase 보안 규칙으로 제한되는지, 서로 다른 브라우저에서 동시 예약 시 중복 예약이 차단되는지 확인한 뒤 실제 고객 예약을 받으세요. GitHub의 공개 저장소에는 관리자 비밀번호나 서비스 계정 비공개 키를 올리지 마세요.

**배포:** Firebase Authentication에서 Email/Password 활성화 및 새 `firestore.rules` 게시 후 GitHub의 `index.html`과 `README.md`를 교체하세요. Cloud Functions는 배포하지 않습니다.

## v5.9 배포 안내 (Spark 무료 요금제)

1. Firebase 콘솔 → Authentication → Sign-in method: **Anonymous + Email/Password** 활성화. 기존 관리자 Email/Password도 계속 사용합니다.
2. Firebase 콘솔 → Firestore Database → Rules: **새 `firestore.rules` 내용을 게시**. 기존 규칙이 고객의 `password` 인증을 막으므로 반드시 교체.
3. GitHub Pages 저장소에서 **`index.html` + `README.md` 교체**. Cloud Functions / Blaze 불필요.
4. 같은 전화번호로 서로 다른 브라우저에서 **새 예약 2건**을 만들고 조회 시험.
5. 이전 익명 계정에 있던 예약은 **그 계정이 남아 있는 동일 브라우저에서 처음 계정을 만들며 연결하는 경우만** 자동 승계. 별도 익명 UID에 있는 과거 예약들은 별도 관리자 지원이 필요.

### 보안 및 제약

- 전화번호 자체는 인증되지 않습니다. **6자리 숫자 비밀번호는 보안 강도가 낮아** 반복 로그인 시도 제한이 중요합니다. 인증 실패 시 Firebase 계정 보호 설정과 모니터링을 확인하세요.
- 비밀번호를 잊으면 별도의 복구 절차가 필요합니다. 이 버전은 고객용 자동 복구 기능이 없습니다.
- 기존 관리자 로그인은 **별도 관리자 계정**으로 유지합니다. 관리자 계정과 고객 계정은 분리되어 있습니다.
- 고객 예약정보는 계정 UID별 Firestore 읽기 권한으로 보호됩니다. Firebase 규칙을 무조건 공개하면 안 됩니다.
- 실제 Firebase 환경에서 통합 테스트를 마친 결과물은 아닙니다. 테스트 데이터로 검증한 뒤 공개하세요.

## v6.0 전체 정보 백업

관리자 로그인 → 상단 **⬇ 전체 정보 백업** 클릭 → `신지암신통사주_전체백업_YYYYMMDDTHHMMSS.json` 파일 저장. 현재 Firebase에 있는 모든 `bookings`, `settings`, `slotLocks` 문서를 다시 읽습니다. 취소·거절한 예약도 포함합니다. 해당 문서 접근 권한이 없으면 다운로드하지 않고 오류를 표시합니다. 자동 복원 기능은 포함되지 않습니다. 이름, 전화번호, 상담 메모 등 개인정보가 들어 있으므로 공유하거나 공개 저장소에 올리지 마세요.

## v6.1 테스트 절차

1. 가상 고객 이름·전화번호와 동일한 6자리 비밀번호로 서로 다른 예약 가능한 시간 2개를 신청합니다.
2. 예약조회에서 같은 이름·번호·비밀번호로 2건이 나오는지 확인합니다.
3. 다른 브라우저에서도 조회가 되는지 확인합니다.
4. 이전 익명 UID로 만든 예약 또는 관리자가 직접 만든 예약은 고객 계정에 자동 연결되지 않습니다. 관리자 백업에서 기록을 확인할 수 있습니다.
5. Firebase Authentication에서 Email/Password가 활성화되어 있어야 합니다.

실제 Firebase 배포 환경에서 자동 통합 검증된 버전은 아닙니다. 고객 데이터를 사용하기 전에 가상 정보로 검증하세요.

## v6.2 유의사항

비밀번호 없이 예약 접수가 가능하도록 변경했으나 비밀번호 계정에 자동 연결되지 않습니다. 브라우저를 바꾸거나 익명 계정이 삭제되면 고객 본인 조회가 불가능할 수 있으며, 그때는 관리자가 예약 상태를 확인해야 합니다. 고객의 모든 예약을 브라우저 구분 없이 안전하게 병합하려면 검증 가능한 계정 복구/본인 확인 절차가 필요합니다.

## v6.3 배포 필수 작업
1. Cloudflare Worker `sintong-saju-lookup`: `worker.js` 코드 전체로 교체 및 Deploy.
2. Secret `FIREBASE_SERVICE_ACCOUNT` 기존 값 유지. Firebase 서비스 계정은 `sintong-saju` 프로젝트에 속해야 함.
3. Cloudflare Turnstile 위젯 생성: 허용 호스트 `cojumkr.github.io` 설정. Secret key를 Worker Secret `TURNSTILE_SECRET`으로 저장.
4. Turnstile **site key**는 이 배포본 `index.html`에 반영되어 있음.
5. GitHub `index.html`, `README.md` 게시. 브라우저를 바꿔 가상 예약 조회를 시험.
6. 추가로 Cloudflare WAF/Rate limiting 정책을 설정해 반복 조회를 제한할 것.

주의: 이름과 전화번호만 아는 사람에게 예약 일정이 노출될 위험이 남아 있다. Turnstile은 봇 대응이지 본인인증이 아니다.
